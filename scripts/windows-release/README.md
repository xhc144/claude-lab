# Windows 软件：自动合并、签名发布与自动更新

声准 Phonica、律影 Motif、音乐粒子宇宙、墨誊 Moteng、鸿雁邮箱这五个 Windows 软件由同一条流水线发布：
[`.github/workflows/ship.yml`](../../.github/workflows/ship.yml)（Actions 里叫「Ship · 自动合并与发布」）。
正常情况下不需要在 GitHub 上做任何操作。

## 平时怎么用

让 AI 修改软件，AI 把改动推送到 `claude/**` 分支即可。之后全部自动：

1. **合并候选**：把分支合并到最新的 `main`。与 `main` 有冲突时停下，并在运行摘要里说明（AI 在分支上合并 `main` 再推送即可）。
2. **定版本号**：对要发布的软件，`package.json` 的版本号如果已经发布过（或者标签已被占用），自动改成下一个补丁号（1.2.3 → 1.2.4），连同 `package-lock.json` 一起提交。想发 1.3.0 或 2.0.0，在分支里把版本号改成它即可，流水线会保留。
3. **Windows 构建与测试**：每个相关软件在 Windows 上各自构建、跑单元测试和自检、静默安装后再测一遍，并用已有的 `WIN_CSC_LINK` / `WIN_CSC_KEY_PASSWORD` 签名。
4. **合并进 main**：分支改动到的软件**全部通过**才合并；任何一个失败，分支不合并，也不发布。
5. **发布**：每个通过测试、已签名、且与上次正式发布相比有改动的软件，各自创建 Release（`<软件>-v<版本>`），再把它的自动更新信息 `<软件>-latest/latest.yml` 推进到新版本。

直接推送到 `main` 也一样，只是少了合并这一步。

### 哪个软件会发布

[`apps.json`](apps.json) 列出每个软件的目录。某个软件的文件与它**上一次正式发布**相比有改动，就发布它（README 等说明文字除外），其他软件不受影响：

| 软件 | 发布标签 | 更新信息 | 目录 |
| --- | --- | --- | --- |
| 声准 Phonica | `phonica-v*` | `phonica-latest` | `phonica/`（不含 `tools/`） |
| 律影 Motif | `motif-v*` | `motif-latest` | `motif/` |
| 音乐粒子宇宙 | `particle-universe-v*` | `particle-universe-latest` | `particle-universe/` |
| 墨誊 Moteng | `moteng-v*` | `moteng-latest` | `moteng/`、`mojing/tex/` |
| 鸿雁邮箱 | `hongyan-mail-v*` | `hongyan-mail-latest` | `hongyan-mail/` |

一个软件测试失败，只影响它自己：它不发布，别的软件照常发布（但如果它正是这个分支改动的软件，分支就不会合并）。

### 提交标题里的开关

只看提交信息的第一行（标题），正文里提到不算：

- `[skip ship]`：这次推送什么都不做。
- `[skip release]`：测试通过后只合并，不发布。

### 安全措施

- **测试失败不发布**：发布只使用本次运行里通过全部测试的那份构建产物，没有签名的构建也不会发布。
- **不会重复发布**：版本标签先通过 API 创建，创建引用是原子操作，同一个版本只可能发布一次；被别的运行抢先时，本次运行放弃这个版本并自动重新排一次。
- **不会版本冲突**：版本号从已有标签推算，已用过的版本不会再用。`main` 在测试期间被别人更新时，只有被测软件的文件与测试时完全相同才合并，否则自动重新测试。
- **更新信息不会被覆盖**：版本发布里的文件从不覆盖（不用 `--clobber`）；`<软件>-latest/latest.yml` 只会指向已发布的最高版本，旧的运行无法把它改回旧版本。Release 先以草稿上传全部文件，全部成功后才公开。

## 手动发布（备用）

Actions → 「Ship · 自动合并与发布」→ **Run workflow**：

| 参数 | 说明 |
| --- | --- |
| 分支 | `main`：只发布；某个 `claude/...` 分支：测试通过后合并再发布 |
| 软件 | `auto`：有改动的软件；`all`：全部；或列出软件，如 `phonica,motif`——列出的软件即使没有改动也会发一个新补丁版本 |
| 发布 | 取消勾选则只测试和合并 |

只想要一个测试安装包（不发布）：运行对应软件自己的工作流（如「phonica · Windows build」），在运行页面的 Artifacts 里下载。

## 已安装的软件如何更新

装好的软件启动后不久读取 `releases/download/<软件>-latest/latest.yml`，之后每 6 小时读一次。发现新版本就在后台下载，核对 SHA-512 和签名，然后：

- 声准 Phonica、墨誊在标题栏显示“重启更新”；Motif、音乐粒子宇宙、鸿雁邮箱弹窗询问是否现在重启；
- 不理会也没关系，下次关闭软件时自动安装。

**签名校验**：新安装包必须由一张本机信任、且名称相同的证书签名（electron-updater 的默认检查）；或者——自签名证书在没导入它的电脑上不被信任——由**与当前已安装程序完全相同的证书**签名，签名本身能用该证书验证，并且文件自签名后没有改动（[`update-signer.cjs`](update-signer.cjs)）。因此任何电脑都能静默更新，而被替换或改动过的安装包仍会被拒绝。每次构建都会在 Windows 上验证这项检查：接受真实安装包，拒绝改了一个字节的副本和别人签名的文件。

几点说明：

- 只有用安装包装的才会自动更新；便携版 zip 不更新（否则会在别处再装一份）。
- `*-latest` 这几个发布页不要删，删了已安装的软件就找不到新版本了（下次发布会自动重建）。
- 出了问题，可以看软件数据目录下的 `logs\updater.log`（鸿雁邮箱在它自己的日志里）。
- 从没有自动更新功能的旧版本（Phonica 1.0.0、Motif 0.9.0、粒子宇宙 1.0.0 便携版、墨誊 1.0.0、鸿雁邮箱 1.1.0 及以前）升级，要手动装一次新安装包，之后就自动了。

## 签名证书

流水线使用仓库 Secrets 中**已有的** `WIN_CSC_LINK`（pfx 的 base64）和 `WIN_CSC_KEY_PASSWORD`，不会生成新证书。构建日志里会显示证书名称、指纹和到期日；离到期不足 30 天时给出警告。发布构建缺少证书时直接失败，不会发布未签名的安装包。

自签名证书只在导入过它的电脑上被 Windows 信任；别人第一次下载安装时仍可能看到“未知发布者”。这不影响自动更新（见上文）。

以下脚本只在需要时使用：

| 文件 | 用途 |
| --- | --- |
| `trust-signing-cert.ps1` | 让另一台电脑信任这张证书（只需要 .cer），可消除安装时的“未知发布者”提示 |
| `new-signing-cert.ps1` | 生成新的自签名证书。**证书已经配置好，平时不要运行**；只在证书丢失或过期时用，并且要用相同的名称，然后替换两个 Secret |

证书丢失或过期后用同名新证书替换，已安装的软件会拒绝新证书签的更新（指纹不同），需要在那些电脑上手动装一次新版本，或先运行 `trust-signing-cert.ps1` 信任新证书。

### 被杀毒软件报毒怎么办

签名不能保证不被报毒。如果 Windows Defender 把你自己的软件报成病毒，到微软的提交页面（搜“Microsoft Security Intelligence 提交文件”）上传那个文件，选“我认为这是误报”。免费，一般几天内有结果。

## 修改了工作流文件的分支

GitHub 不允许 Actions 内置令牌推送 `.github/workflows/` 下的文件，所以**修改了工作流的 `claude/**` 分支**会照常测试，但不会自动合并（运行摘要会说明）。需要时可以：

- 手动合并这一个分支；或
- 一次性授权：创建一个只对本仓库有效的 fine-grained token（权限：Contents 读写、Workflows 读写），保存为仓库 Secret `SHIP_TOKEN`。之后这类分支也会自动合并。

修改软件本身不涉及工作流文件，不受影响。

## 文件

| 文件 | 用途 |
| --- | --- |
| `apps.json` | 每个软件的目录、发布文件、工作流 |
| `plan.mjs` | 决定这次构建、合并前必须通过、以及发布哪些软件 |
| `bump.mjs` | 给要发布的软件定版本号 |
| `land.mjs` | 测试通过后把候选提交合并进 main（处理并发） |
| `publish.mjs` | 创建 Release、上传文件、推进更新信息 |
| `update-feed.mjs` | 把 electron-builder 的 `latest.yml` 改成指向版本发布页的绝对地址，并核对大小与校验码 |
| `check-build.ps1` | 每个软件构建后在 Windows 上检查签名、更新文件和更新签名校验，生成 SHA256SUMS |
| `update-signer.cjs` | 已安装软件下载更新后使用的签名检查；每个软件里有一份相同的副本（`check-copies.mjs` 保证一致） |
| `notes/<软件>.md` | Release 说明模板（自动附上自上次发布以来的改动） |
| `tests/` | 上述脚本的测试：`node --test scripts/windows-release/tests/*.test.mjs` |
